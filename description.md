# Reference-conditioned kernel generation для cross-domain few-shot similarity

## 1. Задача

Цель — сравнивать изображения новых классов, которых не было среди классов обучения. Для пары изображений модель выдаёт similarity; качество измеряется по тому, насколько часто случайно выбранная пара одного класса получает больший score, чем пара разных классов.

Эксперимент построен как leave-one-dataset-out (LOOCV): один датасет целиком служит целевым доменом, остальные пять — source-доменами для базового энкодера. На целевом домене для каждого класса выбираются `K` support-изображений для адаптации и 10 отдельных query-изображений для оценки. Использованы `K = 5, 10, 15` и пять seed для каждого фолда.

## 2. Предлагаемая архитектура

Общий энкодер — ResNet18, обученный на source-данных. В основных сравнениях его параметры заморожены при адаптации на target. Для Hyper и Hyper-Sym используется уровень `layer4` (512 × 7 × 7): из референсного изображения генерируются два персонализированных свёрточных ядра 3 × 3, каждое с 16 выходными каналами. Ядра применяются к карте признаков второго изображения grouped convolution; после BatchNorm, GELU и global average pooling признаки конкатенируются, а MLP выдаёт score сравнивателя.

Однонаправленный Hyper добавляет выход головы к cosine similarity эмбеддингов:

`s(a,b) = cos(e(a),e(b)) + α h(a→b)`.

Коэффициент `α` инициализирован нулём. Hyper-Sym усредняет выходы головы в обоих направлениях `a→b` и `b→a`, сохраняя общий cosine residual. Hyper-Pure использует обучаемый выход головы без cosine residual. Nonspatial — абляция с одним глобально сгенерированным ядром.

Во время адаптации Hyper-сравнивателей оптимизируются генератор и голова по support-парам: все позитивные сочетания внутри класса и сопоставимое количество негативных пар. Используется BCE-with-logits по `5 × similarity`, пять эпох адаптации и AdamW с `lr=3e-4`. Query изображения не участвуют в этой оптимизации.

## 3. Сравниваемые методы

В основном LOOCV-прогоне все методы начинаются с одного и того же source-checkpoint и получают одинаковые support/query выборки. Энкодер заморожен для всех методов, кроме метода Fine-tune.

- **Cross-domain baseline** — cosine similarity эмбеддингов без target-адаптации.
- **ProtoNet** — прототипы классов вычисляются по support, query эмбеддинги сравниваются с прототипами; pair score — similarity posterior-векторов двух изображений.
- **Linear** — линейный probe, обученный на support.
- **CosClf** — cosine classifier на support.
- **RelationNet** — обучаемая MLP-голова на эмбеддингах пары, без генерации ядер.
- **BN-adapt** — обновление статистик BatchNorm по support.
- **Fine-tune** — target-адаптация `layer4` и embedding head исходной сиамской модели.
- **RelationGCN** — task-specific support-guided адаптация, подробнее ниже.
- **Nonspatial, Hyper-Pure, Hyper, Hyper-Sym** — варианты reference-conditioned сравнивателя.

### Что именно здесь называется RelationGCN

Это адаптация идеи support-guided пространственного усиления признаков, а не точное воспроизведение оригинального RelationGCN и его исходного протокола обучения. Замороженная ResNet18 вычисляет `layer3`-карты (256 каналов). По карте референса генерируются локальные depthwise-ядра размером 3 × 3 для каждой пространственной позиции и каждого канала; их ответы смешиваются, а усиление добавляется через обучаемый residual gate. Оценка пары симметрична, а энхансер обучается на target support; исходный энкодер остаётся замороженным.

Реализация намеренно избегает глобальных полно-связных `C × C` ядер: они давали бы очень большой генератор и стоимость. Текущий RelationGCN — отдельная облегчённая per-position depthwise адаптация. Поэтому выводы относятся именно к этому варианту. В частности, старые запуски до исправления реализации RelationGCN не следует объединять с новыми таблицами: старое ранжирование (включая победы на Cars, Flowers и Aircraft, о которых сообщил пользователь) было получено другой версией кода. В новых финальных прогонах RelationGCN лидирует на Flowers, а Hyper-Sym — на остальных пяти фолдах.

## 4. Датасеты и протокол выборок

Использованы шесть целевых доменов: CUB200, Cars196, Stanford Dogs, Oxford Flowers 102, NABirds и FGVC Aircraft. В каждом фолде каждый из пяти source-доменов ограничен единым глобальным бюджетом 50 классов × 27 изображений на класс, то есть 1 350 изображений на домен и 6 750 изображений на фолд. Число классов ограничено Aircraft (50), число изображений на класс — NABirds (27).

В target-фолде выбрано 50 классов. Их подмножество фиксировано между seed; support и query изображения перемешиваются отдельным seed, не пересекаются, а число query равно 10 на класс. Для NABirds модель оценивается на фиксированной выборке из 50 классов, хотя исходный набор содержит 550 классов в используемом split.

При вычислении pair-accuracy из query-классов на каждый класс случайно берутся пять позитивных пар и пять негативных пар. Затем сравниваются все полученные позитивные и негативные scores. Это оценка pair-accuracy по сэмплированным парам, а не перебор всех возможных пар изображений. Каждый результат в таблицах — среднее по пяти seed; `±` показывает среднеквадратичное отклонение между seed внутри фолда. Сводные числа по шести фолдам — невзвешенное среднее fold-level mean и fold-level std соответственно.

Hyper-Sym имеет наибольшее среднее по фолдам при всех трёх K и выигрывает у RelationGCN на пяти доменах из шести. RelationGCN выигрывает на Flowers при каждом K. Результаты Hyper-Sym нельзя свести к общему выигрышу на каждом домене: разрыв между методами зависит от набора данных. Например, на Dogs при K=15 Hyper-Sym опережает RelationGCN на 7.25 п.п., тогда как на Flowers RelationGCN выше на 1.08 п.п. Последние разницы являются описательными; при пяти seed их не следует трактовать как строгий тест статистической значимости.

## 6. Отдельная ветка: fine-tuning энкодера + методы, K=10

Дополнительно выполнен LOOCV-прогон с `--finetune`. Для каждого фолда и seed размораживались `layer4` и embedding head; использовалось до 15 эпох с ранней остановкой, а 20% support-картинок каждого класса отводились под внутреннюю валидационную выборку. После этого применялась указанная голова/адаптация. Этот протокол отличается от основной таблицы с замороженным энкодером и не должен смешиваться с ней.

| ProtoNet | 0.8552 ± 0.0152 | 16.6 с | 485 MB |
| Linear | 0.8141 ± 0.0149 | 16.6 с | 574 MB |
| RelationNet | 0.7236 ± 0.0230 | 16.7 с | 552 MB |

Лучшие комбинации по отдельным target-фолдам: ProtoNet — CUB, Dogs, Flowers и NABirds; Hyper-Sym — Cars; RelationGCN — Aircraft. Хотя fine-tuning повышает результат части методов, Hyper-Sym в среднем не улучшился относительно основной frozen-версии при K=10 (0.8577 против 0.8663). Значит, дополнительное обучение энкодера не даёт универсального выигрыша. Ранее упомянутый неудачный end-to-end эксперимент был отдельной попыткой, в эти измерения и таблицы он не входит.

### Исправление времени обучения

В `cross_validate.py` общий wall-time уже охватывал fine-tuning энкодера, однако отдельная колонка `train_time_s` раньше не включала `finetune_encoder()` и могла показывать `0.0` для ветки без дополнительной обучаемой головы. Теперь время fine-tuning суммируется со временем обучения последующей головы/адаптера. В новом CSV все 54 значения `*_train_time_s_mean` (9 методов × 6 фолдов) ненулевые. Wall-time по-прежнему включает весь этап модели; infer-time для части пользовательских моделей отдельно не профилируется, поэтому для сравнения полной стоимости следует использовать `total_time_s_mean`.

## 7. Controlled comparison: dense RelationGCN at K=10

Чтобы проверить, не была ли предыдущая RelationGCN просто более выразительной, добавлен отдельный вариант `relationgcn-full`. Он восстанавливает dense-вариант из сохранённого старого дизайна: вектор референсного `layer3` признака генерирует четыре полных `256×256×3×3` ядра; каждое ядро смешивает каналы и действует на всём пространственном поле. Некорректный старый вызов `conv2d` заменён математически эквивалентной grouped convolution с отдельной группой на каждый пример. Это контролируемая реконструкция старой идеи, а не точная копия неизвестного файла, которым были получены исторические CSV.

Прогон выполнен на тех же текущих source-checkpoint-ах и одинаковых support/query выборках, что и K=10 таблица выше: шесть фолдов, пять seed, 10 query на класс, 15 эпох обучения адаптера. Сводные pair-accuracy:

| Фолд | Dense `relationgcn-full` | Depthwise RelationGCN | Hyper-Sym |
|---|---:|---:|---:|
| CUB | 0.8731 ± 0.0132 | 0.8616 ± 0.0170 | **0.8869 ± 0.0220** |
| Cars | **0.8228 ± 0.0126** | 0.7617 ± 0.0217 | 0.8177 ± 0.0102 |
| Dogs | 0.8841 ± 0.0194 | 0.8519 ± 0.0116 | **0.9330 ± 0.0120** |
| Flowers | **0.9519 ± 0.0096** | 0.9274 ± 0.0084 | 0.9245 ± 0.0147 |
| NABirds | **0.8359 ± 0.0175** | 0.7986 ± 0.0259 | 0.8307 ± 0.0171 |
| Aircraft | **0.8453 ± 0.0139** | 0.7918 ± 0.0195 | 0.8047 ± 0.0224 |
| **Mean over folds** | **0.8689 ± 0.0144** | 0.8322 ± 0.0174 | 0.8663 ± 0.0164 |

В этом контролируемом сравнении dense-вариант превосходит depthwise RelationGCN на всех шести фолдах (в среднем +3.67 п.п.) и немного превосходит Hyper-Sym по среднему (+0.26 п.п.), хотя Hyper-Sym остаётся лучше на CUB и Dogs. Dense-версия лучше Hyper-Sym на Cars, Flowers, NABirds и Aircraft. Поэтому старая RelationGCN действительно, вероятно, выигрывала у новой облегчённой реализации главным образом за счёт большей ёмкости; формулировка «RelationGCN в целом лучше» слишком широкая.

Цена этой ёмкости велика: генератор содержит около 153.4M параметров против примерно 0.63M у depthwise-версии. На RTX 4070 SUPER dense-вариант занимал в среднем около 311 секунд и 3.1 GB на fold/seed, depthwise-вариант — около 57 секунд и 0.75 GB при K=10. Результаты с пяти seed и всего 50 target-классами пока недостаточны, чтобы объявлять преимущество в +0.26 п.п. над Hyper-Sym статистически убедительным.

Полная таблица этого прогона сохранена в `results/final_relationgcn_full_k10.csv`. Его можно повторить аргументом `--arches relationgcn-full` при том же наборе параметров K=10.

Для K=10 исправленные ProtoNet-поля записаны в `final_loocv_k10.csv`; прежний ProtoNet-столбец был ошибочно равен baseline. Старые промежуточные CSV и логи удалены из рабочей папки; они не являются источником таблиц выше.

Все Python-команды запускались из корня проекта через `.venv\Scripts\python.exe`. Схема основного прогона:

```powershell
foreach ($K in 5, 10, 15) {
  .\.venv\Scripts\python.exe -u scripts\cross_validate.py `
    --datasets cub,cars,dogs,flowers,nabirds,aircraft `
    --arches protonet,linear,relationnet,relationgcn,bnadapt,nonspatial,hyper-pure,hyper,cosclf,finetune,hyper-sym `
    --seeds 1,2,3,4,5 --K $K --M-per-class 10 `
    --neg-same-domain-ratio 0.5 --lr-side 3e-4 --adapt-epochs 5 `
    --feature-level l4 --n-kernels 2 --out-ch 16 `
    --output "results/final_loocv_k$K.csv"
}
```

Отдельная finetune-комбинация запускалась с теми же датасетами, seed и K=10, параметрами fine-tuning по умолчанию и `--finetune`; результаты сохранены в `results/final_loocv_k10_finetune.csv`.

**Источник baseline-энкодеров.** В этих прогонах `cross_validate.py` загрузил существующие `baseline_loo_<fold>.pt` cache-файлы, а не переобучал шесть source-энкодеров. Логи прежнего основного запуска показывают для них тот же budget 50 × 27 и запись cache-чекпойнтов. В самих checkpoint есть только веса `tower` и `head`, без конфигурации и метаданных обучения, поэтому их полное происхождение независимо проверить нельзя. Seed-ы в новых CSV измеряют вариацию support/query и адаптации при этих фиксированных энкодерах; это не пять независимых обучений ResNet. Для полностью свежей репликации нужно удалить/игнорировать эти cache-файлы через `--skip-baseline-cache` и заново выполнить все фолды и K.

## 9. Насколько надёжны выводы

Таблицы теперь согласованы по числу фолдов, K, размеру query и числу seed; значения ProtoNet и время fine-tuning исправлены. Поэтому они надёжнее первоначальных результатов из старых `loocv_k*.csv`. Тем не менее это исследовательские результаты, а не окончательное подтверждение превосходства:

1. Пять seed варьируют выборки и адаптацию, но encoder checkpoint фиксирован; вариация обучения самого source-энкодера не измерялась.
2. Оценка pair-accuracy основана на небольшом числе случайных пар на класс, а не на полном переборе пар; это добавляет sampling noise.
3. Проверяется фиксированное подмножество из 50 target-классов на датасет. Для NABirds это только часть доступных классов.
4. RelationGCN является нашей task-adapted архитектурой, не точным paper reproduction; старые результаты старой реализации нельзя сравнивать напрямую с новыми.
5. Кэш baseline содержит только веса без полного provenance. Для наиболее строгого воспроизведения нужен повторный запуск с принудительным обучением энкодеров.

В рамках этих ограничений основной эмпирический вывод такой: при данном протоколе Hyper-Sym устойчиво силён и имеет лучшее среднее качество среди сравнённых методов для K=5, 10 и 15; RelationGCN-адаптация — близкий конкурент и лучше на Flowers, но требует больше времени и памяти. Fine-tuning энкодера даёт неодинаковый эффект для разных голов и не улучшает Hyper-Sym в среднем.

## 10. Related works

### Условная генерация свёрточных фильтров

- **Dynamic Filter Networks** — De Brabandere et al. вводят фильтры, генерируемые динамически в зависимости от входа. Это фундаментальная идея, ближайшая к механизму Hyper, где признаки референсного изображения задают свёрточные ядра для обработки второго изображения: [статья NeurIPS 2016](https://papers.neurips.cc/paper_files/paper/2016/file/8bf1211fd4b7b94528899de0a43b9fb3-Paper.pdf).
- **HyperNetworks** — Ha, Dai и Le описывают нейросеть, которая генерирует параметры другой нейросети. Это общий источник для гиперсетей, а не описание конкретной архитектуры проекта: [статья ICLR 2017](https://openreview.net/pdf?id=rkpACe1lx).
- **Learning Instance and Task-Aware Dynamic Kernels for Few-Shot Learning** — Ma et al. применяют генерируемые динамические ядра в few-shot задачах. Это близкий по постановке пример, но их модель формирует instance- и task-aware ядра и отличается от используемого здесь Hyper: [arXiv:2112.03494](https://arxiv.org/abs/2112.03494).

### Сравнение пар и few-shot обучение

- **Learning to Compare: Relation Network for Few-Shot Learning** — Sung et al. обучают глубокую функцию сравнения пары примеров. Эта работа относится к baseline RelationNet в экспериментальных таблицах; она не является точным источником Hyper или RelationGCN: [CVPR 2018](https://openaccess.thecvf.com/content_cvpr_2018/html/Sung_Learning_to_Compare_CVPR_2018_paper.html).
- **Prototypical Networks for Few-shot Learning** — Snell, Swersky и Zemel задают прототипный baseline, который вычисляет представление класса как центр support-примеров в пространстве признаков: [NeurIPS 2017](https://proceedings.neurips.cc/paper_files/paper/2017/hash/cb8da6767461f2812ae4290eac7cbc42-Abstract.html).
- **Few-Shot Learning with Graph Neural Networks** — Garcia и Bruna рассматривают few-shot inference как передачу сообщений по графу support/query. Это релевантный графовый контекст, но текущая RelationGCN-адаптация не строит такой граф: [ICLR 2018](https://openreview.net/pdf?id=BJj6qGbRW).

### RelationGCN и границы адаптации

- **Few Shot Object Detection for SAR Images via Feature Enhancement and Dynamic Relationship Modeling** — Chen et al. описывают RelationGCN для few-shot обнаружения объектов в SAR-изображениях: attention для support, support-guided усиление query-признаков и графовую модель отношений. В этом проекте название RelationGCN относится к адаптации той линии идей под попарное сравнение обычных изображений. Текущий код использует локальные depthwise-ядра и симметричное cosine-сравнение, не Faster R-CNN и не исходный графовый модуль; поэтому это не reproduction статьи: [Remote Sensing, 2022, 14(15), 3669](https://www.mdpi.com/2072-4292/14/15/3669), [DOI: 10.3390/rs14153669](https://doi.org/10.3390/rs14153669).
- Для базового графового оператора статья RelationGCN ссылается на **Semi-Supervised Classification with Graph Convolutional Networks** — Kipf и Welling: [arXiv:1609.02907](https://arxiv.org/abs/1609.02907). Графовый оператор из этой работы в текущем depthwise-адаптере напрямую не реализован.
